# Cobrança automática (Asaas) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Customers subscribe to Intermediário/Completo (monthly or yearly) through Asaas with Pix, card or boleto. `user.plan` follows the payments automatically, and the owner can grant permanent "cortesia" plans.

**Architecture:** A pure rules function `(subscription state, event, now) → (new state, effective plan, remote actions)` holds every billing decision. Thin DB modules apply it inside a transaction, and the only writer of `user.plan` for subscribers is that module. Three entry points feed it: the Asaas webhook (token-checked, idempotent by event id, re-reads the payment from the Asaas API), a daily cron tick for deadlines, and the customer's own server actions (subscribe, change plan, cancel). Access control (`access.ts`, `requireViewer`) does not change.

**Tech Stack:** Next.js 16.4 App Router (server actions, route handlers), Drizzle + PostgreSQL, Zod 4, Pino, Vitest, Asaas REST API v3 via `fetch` (no SDK).

**Spec:** `docs/superpowers/specs/2026-10-19-cobranca-design.md` (approved 2026-10-19). Read it before any task.

## Global Constraints

- Branch `feature/cobranca`, cut from `main` **after** PR gabrielrichardy/nichemap#28 is merged. Open a PR at the end. No pre-commit hooks.
- Prices (`src/lib/billing-plans.ts`): Intermediário R$ 59,90/month and R$ 599,00/year. Completo R$ 99,90/month and R$ 999,00/year. Básico stays free and is not sold.
- Grace period: 3 days after the due date. Cancel at Asaas after 30 days overdue. A pending checkout is abandoned after 30 days.
- Env (server only, Zod-validated in `env-schema.ts`):
  - `ASAAS_API_KEY`
  - `ASAAS_WEBHOOK_TOKEN`, 32–255 chars, no spaces
  - `ASAAS_ENV`, `sandbox` | `production`, default `sandbox`
  - Missing key or token → checkout shows "Assinaturas indisponíveis no momento" and the site still works.
- Asaas base URLs: sandbox `https://api-sandbox.asaas.com/v3`, production `https://api.asaas.com/v3`. Auth header `access_token`. Check both against docs.asaas.com before Task 1 and record the source in `docs/setup.md`.
- Never store CPF/CNPJ or card data. Never log the API key, webhook token, CPF or full response bodies.
- `src/app` and `src/components` never import `@/db`. Files ≤ 350 lines. UI copy in pt-BR. Mobile-first: no horizontal scroll at 375 px.
- Migrations: `npm run db:generate` and review the SQL. Never run `db:migrate` against production without the owner's OK.
- No live Asaas account, live key or real money without the owner's explicit OK. Everything is tested in the sandbox.
- Done: `npm run check` green, plus the sandbox walkthrough in Task 9.

## Review Focus

1. **The same payment's events arrive out of order or twice** (OVERDUE delivered after RECEIVED, or a resend). The decision comes from the payment status re-read from the API, so a stale event changes nothing. Test in Task 5.
2. **A webhook for a subscription the app doesn't know** (an old cancelled one, or a charge created by hand in the Asaas panel). Answer 200 and ignore it, never 500: Asaas pauses the whole queue after 15 consecutive failures. Test in Task 5.
3. **Double click on "Assinar", or two tabs.** It must not create two remote subscriptions. A pending row with a remote id reuses that subscription's first invoice URL. Test in Task 4.
4. **CPF/CNPJ typed with dots, dashes or wrong check digits.** Strip the formatting and validate the check digits before calling Asaas. A wrong number shows "CPF ou CNPJ inválido" and makes no API call. Test in Task 6.
5. **Asaas down or erroring during subscribe, cancel or account deletion.** The local state does not change, the customer sees an error, and account deletion does not happen. Tests in Task 4 and Task 8.

**Files:**

**Interfaces:**
- `billing-plans.ts`:
  - `type PaidPlan = "intermediario" | "completo"`
  - `type Cycle = "monthly" | "yearly"`

- `billing-rules.ts`:
  - `type BillingStatus = "pending" | "active" | "overdue" | "suspended" | "canceled" | "ended"`
    - `suspended`: dropped to Básico for non-payment while the charge is still open at Asaas
    - `canceled`: cancelled, but paid until `periodEnd`
  - `interface BillingState { status: BillingStatus; plan: PaidPlan; cycle: Cycle; periodEnd: Date | null; overdueSince: Date | null; scheduledPlan: PaidPlan | null; createdAt: Date }`
  - `type BillingEvent =` one of:
    - `{ type: "paid"; dueDate: Date }`
    - `{ type: "overdue"; dueDate: Date }`
    - `{ type: "refunded" }`
    - `{ type: "chargeback" }`
    - `{ type: "remote_deleted" }`
    - `{ type: "customer_cancel" }`
    - `{ type: "tick" }`
  - `interface BillingOutcome { state: BillingState; cancelRemote: boolean }`
  - `applyBillingEvent(state: BillingState, event: BillingEvent, now: Date): BillingOutcome`
  - `effectivePlan(state: BillingState): Plan`. It returns `state.plan` for active, overdue and canceled, and `"basico"` for the rest.
  - `isPlanLockedBy(status: BillingStatus | null): boolean`. It is true for every status except `ended` and null.
  - `GRACE_DAYS = 3`, `CANCEL_AFTER_DAYS = 30`, `ABANDON_AFTER_DAYS = 30`

- [ ] **Step 1: Write failing tests.** One `it` per rule below, with fixed dates (`now = new Date("2026-11-10T12:00:00Z")`):
  - **paid**
    - From pending: becomes active, `periodEnd = dueDate + 1 month` (monthly) or `+ 1 year` (yearly), `overdueSince` null.
    - From overdue or suspended: becomes active. `periodEnd` extends from the later of the current `periodEnd` and `dueDate + cycle`.
    - With `scheduledPlan` set: `plan = scheduledPlan`, then `scheduledPlan = null`.
    - On `ended`: changes nothing.
  - **overdue**
    - From active: becomes overdue with `overdueSince = dueDate`.
    - On any other status: changes nothing.
  - **tick**
    - overdue with `now ≥ overdueSince + 3d`: becomes suspended.
    - overdue or suspended with `now ≥ overdueSince + 30d`: becomes ended, `cancelRemote: true`.
    - canceled with `now ≥ periodEnd`: becomes ended, `cancelRemote: false`.
    - pending with `now ≥ createdAt + 30d`: becomes ended, `cancelRemote: true`.
    - Otherwise: changes nothing.
  - **refunded / chargeback** (any status except ended): becomes ended, `cancelRemote: true`.
  - **remote_deleted**: canceled or ended → no change (our own cancel echoes back from Asaas). Active or overdue with `periodEnd > now` → canceled. Otherwise → ended. `cancelRemote: false`.
  - **customer_cancel**
    - pending: becomes ended, `cancelRemote: true`.
    - active, overdue or suspended with `periodEnd > now`: becomes canceled, `cancelRemote: true`.
    - suspended with `periodEnd ≤ now`: becomes ended, `cancelRemote: true`.
  - **effectivePlan**: one test per status.
  - **isPlanLockedBy**: one test per status, plus null.

### Task 4: Customer billing module (subscribe, change, cancel)

**Files:**
- Create: `src/lib/billing.ts`, `src/lib/billing.db.test.ts`, `src/lib/cpf-cnpj.ts`, `src/lib/cpf-cnpj.test.ts`

**Interfaces:**
- Consumes: Task 1 client, Task 2 rules, Task 3 tables.
- `cpf-cnpj.ts`: `normalizeCpfCnpj(input: string): string | null`. It returns the digits when it is a valid CPF (11 digits) or CNPJ (14 digits) by check digits, and null otherwise.
- `billing.ts`:
  - `type CheckoutResult = { ok: true; url: string } | { ok: false; reason: "unavailable" | "invalid_document" | "already_subscribed" | "complimentary" | "provider_error" }`
  - `startCheckout(input: { userId: string; name: string; email: string; plan: PaidPlan; cycle: Cycle; cpfCnpj: string; mobilePhone?: string }, now?: Date): Promise<CheckoutResult>`. Rules, in order:
    1. Config is null → `unavailable`.
    2. The document is invalid → `invalid_document`.
    3. The user is complimentary → `complimentary`.
    4. A row is pending → return its `firstInvoiceUrl`.
    5. A row is active, overdue or suspended → `already_subscribed`.
    6. A row is canceled with `periodEnd > now`:
       - create a remote subscription with `nextDueDate = periodEnd`
       - set the row to active, keeping `plan` and `periodEnd`, with `scheduledPlan = plan`, the new `cycle` and the new remote id
       - return `/conta`
    7. Otherwise: create the customer (reuse `asaasCustomerId` if a row exists) and a subscription with `nextDueDate = today`. Upsert the row as pending, store `firstInvoiceUrl` and return it.
    - Any `AsaasError` → `provider_error`, with no DB write.
  - `changePlan(userId: string, plan: PaidPlan): Promise<{ ok: boolean }>`. Allowed only when active.
    - Always call `updateSubscriptionValue` first.
    - Monthly upgrade: set `plan` and write `user.plan` now.
    - Downgrade or yearly upgrade: set `scheduledPlan`.
  - `cancelSubscription(userId: string, now?: Date): Promise<{ ok: boolean }>`. It applies `customer_cancel`. When `cancelRemote` is true, it calls `deleteSubscription` before writing. If the remote call fails, nothing is written.
  - `getBillingSummary(userId: string, now?: Date): Promise<{ status: BillingStatus; plan: PaidPlan; cycle: Cycle; periodEnd: Date | null; overdueSince: Date | null; scheduledPlan: PaidPlan | null; invoiceUrl: string | null } | null>`. It applies a `tick` first and saves it if the state changed (the spec also checks deadlines on page load).
  - Internal helper, exported for Task 5: `saveOutcome(tx, userId: string, outcome: BillingOutcome): Promise<void>`. It updates the row and sets `user.plan = effectivePlan(state)` in the same transaction. It is the only writer of `user.plan` for subscribers.

### Task 5: Webhook and daily tick

**Files:**
- Create: `src/lib/billing-sync.ts`, `src/lib/billing-sync.db.test.ts`, `src/app/api/billing/webhook/route.ts`, `src/app/api/billing/webhook/route.test.ts`, `src/app/api/cron/billing/route.ts`
- Modify: `vercel.json` (add `/api/cron/billing`, schedule `0 12 * * *`)

**Interfaces:**
- `billing-sync.ts`:
  - `isAuthorizedWebhook(token: string | null): boolean`. Constant-time comparison, same approach as `cron.ts`.
  - `handleAsaasEvent(event: { id: string; event: string; payment?: { id: string }; subscription?: { id: string } }, now?: Date): Promise<"processed" | "duplicate" | "ignored">`
    1. Insert the `billing_event`. If it already exists with `processedAt` set, return `"duplicate"`.
    2. Map the event to a rule:
       - `PAYMENT_CONFIRMED` / `PAYMENT_RECEIVED` → paid, only if the re-read payment status is in `CONFIRMED`, `RECEIVED` or `RECEIVED_IN_CASH`
       - `PAYMENT_OVERDUE` → overdue, only if the re-read status is `OVERDUE`
       - `PAYMENT_REFUNDED` → refunded
       - `PAYMENT_CHARGEBACK_REQUESTED` → chargeback
       - `SUBSCRIPTION_DELETED` / `SUBSCRIPTION_INACTIVATED` → remote_deleted
       - Anything else → ignored. Confirm the exact names in docs.asaas.com "Eventos para cobranças/assinaturas" before Step 3.
    3. For payment events, call `getPayment` and find the row by `payment.subscription`. If there is no row, return `"ignored"`.
    4. Apply the rule. Run `deleteSubscription` when `cancelRemote`. Save with `saveOutcome`. Set `processedAt`.
    - Throwing leaves `processedAt` null, so the Asaas resend reprocesses the event.
  - `runBillingTick(now?: Date): Promise<{ changed: number; failed: number }>`. It applies `tick` to every row with status pending, overdue, suspended or canceled. A failure on one row is counted and logged, and does not stop the others.
- Webhook route `POST`: bad token → 401. Invalid JSON or no `id` → 400. `handleAsaasEvent` throws → 500. Otherwise 200 `{ received: true }`. It does not require login.
- Cron route `GET`: `isAuthorizedCron` → 401, the same as `cron/snapshot`.
